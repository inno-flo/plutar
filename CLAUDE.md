# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Plutar (bundle id `com.innoflo.plutar`) is a "read it later" app for links shared from Safari or any other app's share sheet: it collects them, groups them by day or by source, and tracks read/unread. iOS app + macOS port + one share extension per platform, all syncing through CloudKit.

## Project generation — always edit `project.yml`, never the `.xcodeproj` by hand

The Xcode project is generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen) from `project.yml`. After changing `project.yml` (new source path, new entitlement, new build setting), regenerate:

```bash
xcodegen generate
```

Do not hand-edit `Plutar.xcodeproj/project.pbxproj` — regenerating overwrites it. `project.yml` is also the single place that documents which files each of the four targets compiles (see "Targets and sharing" below) and carries `&appGroupID`/`&cloudKitContainerID` YAML anchors so the App Group and CloudKit container identifiers are typed once and referenced everywhere else.

Building through `xcodebuild` (see below) *silently* regenerates some Xcode-managed build settings in `project.pbxproj` as a side effect (signing identity, `PROVISIONING_PROFILE_SPECIFIER`, etc.) even though the file is meant to be fully generated — treat any resulting diff to `Plutar.xcodeproj/project.pbxproj` as noise from the build, not an intentional change, and `git checkout` it back rather than committing it.

## Build

No test target exists in this repo — there's nothing to `xcodebuild test`. Build to verify changes compile:

```bash
# iOS app (simulator, no device needed to verify a build)
xcodebuild -scheme Plutar -configuration Debug -destination 'generic/platform=iOS Simulator' build

# macOS app
xcodebuild -scheme PlutarMac -configuration Debug -destination 'platform=macOS' build
```

Other schemes: `PlutarShare` (iOS share extension), `PlutarShareMac` (macOS share extension) — both also build as dependencies of the two app schemes above, so building the app schemes is usually enough.

The iOS Simulator control/panel tool does not work on this machine (Xcode 27 beta) — verify iOS builds with the `xcodebuild` command above, not the simulator tool.

## Targets and sharing

Four XcodeGen targets, each listing its own `sources:` in `project.yml`:

- **Plutar** (iOS app) — `Plutar/` (its own `App/`, `Views/`, etc.), excluding `Views/macOS/**`.
- **PlutarMac** (macOS app) — `PlutarMac/` plus an explicit allow-list of iOS-tree files/folders it reuses: `Models/`, `Persistence/`, `ViewModels/`, `Views/Rows/LinkRowView.swift`, `Views/FlipCard.swift`, `Views/EmptyStateView.swift`, `Views/SettingsSections.swift`, `Views/macOS/`, and `Assets.xcassets`.
- **PlutarShare** (iOS share extension) / **PlutarShareMac** (macOS share extension) — each its own `Info.plist`/entitlements, plus `Models/LinkItem.swift`, `Models/SourceRank.swift`, `Persistence/`, and `Views/ShareView.swift` shared with the main apps.

There's no separate Swift package or framework — cross-platform code lives directly under `Plutar/` and is included into the other three targets file-by-file via `project.yml`. When adding a new shared file, add its path to every target in `project.yml` that needs it (then `xcodegen generate`); a `#if os(iOS)` / `#if os(macOS)` / `#if canImport(UIKit)` / `#if canImport(AppKit)` split inside one shared file is preferred over duplicating the file per platform.

## Data flow: one on-disk store, shared by 4 processes, synced via CloudKit

`Plutar/Persistence/SharedStore.swift` is the one place all four targets build their `ModelContainer` from — same App Group SQLite file (`group.com.innoflo.plutar` → `Plutar.sqlite`) and the same private CloudKit container (`iCloud.com.innoflo.plutar`), so:

- A link saved by either share extension appears in its platform's main app immediately (same on-disk file, no round trip needed).
- CloudKit syncs that same store across devices/platforms in the background. `AppContainerBootstrap` (shared by `PlutarApp.init`/`PlutarMacApp.init`) builds this container and falls back to a throwaway in-memory one if the on-disk/CloudKit store can't be opened, surfacing a "Stockage indisponible" alert instead of crashing.
- **CloudKit only syncs `LinkItem`/`SourceRank` model fields — never the downloaded thumbnail JPEGs.** Those live in `SharedStore.thumbnailsDirectoryURL()` (also inside the App Group container, so app↔extension sees them immediately) but are per-device: a thumbnail fetched by one device is invisible to another until that device fetches its own copy. `LinkMetadataEnricher.redownloadMissingThumbnails` exists specifically to notice a synced-in `thumbnailFileName` whose file isn't actually on disk and re-fetch just the image (title/excerpt, which did sync, are left alone).
- `LinkMetadataEnricher` (`@MainActor`, runs only in the main apps — network + image decoding don't fit an extension's execution budget) fills in what a share extension couldn't get from the source app: a real title in place of the host-name fallback, an excerpt, and a preview image, via `LPMetadataProvider`. Triggered from `PlutarApp`/`PlutarMacApp` on cold start, on every `scenePhase` transition to `.active` (covers links shared while the app wasn't running), from the manual refresh affordance (iOS: pull-to-refresh on the feed list; macOS: the toolbar's arrow.clockwise button — see `RootView`/`MacFeedList`), and — iOS only — on a debounced `.NSPersistentStoreRemoteChange` notification, which also force-rolls-back the main context so a remotely-merged link that arrived already fully enriched (nothing left for the enricher to save, so nothing would otherwise nudge the running context to refetch) still shows up without waiting for the next launch.
- `LinkRowView` plays its flip animation (`FlipCard`, shared cross-platform SwiftUI, not UIKit-only despite what an older comment nearby might say) whenever a link's title changes from a fallback to something real, or `thumbnailFileName` goes from `nil` to set — covering both the normal first-enrichment case and the cross-device thumbnail-resync case above.
- iOS additionally registers for CloudKit's silent push (`AppDelegate`, `UIBackgroundModes: remote-notification`) so a remote change is pulled the moment it happens while foregrounded, not just on next launch/foreground.
- There is no supported API to force CloudKit to sync sooner than it decides to — the manual refresh affordances above only re-run local enrichment (which happens to be the only client-triggerable part of catching up), they don't ask CloudKit for new data directly.

## Display settings are per-device, not synced

Theme, appearance (light/dark/auto), font, layout, "show thumbnails", "black soir background", shake-to-change-theme (iOS only) are `@AppStorage`/`UserDefaults`, deliberately outside the CloudKit-synced model — they're UI preference, not content. `DisplaySettingsKey` centralizes the raw string keys so `RootView`, `MacRootView`, and `MacSettingsView` (each declares its own `@AppStorage` properties — the property-wrapper model doesn't let them share one instance) can't drift onto different key spellings.

## Feed grouping/modes

`FeedMode` (`.chrono` "À lire", `.source` "Sources", `.read` "Lus") and `FeedGrouping` (pure grouping logic: which items are visible per mode, bucketed into day groups for chrono/read or host groups for source, plus French day-label formatting incl. "1er", the current-year-omitted date suffix) are shared between iOS's `RootView` and macOS's `MacFeedList`/`MacSidebarView` so both group identically without duplicating the logic. `FeedGroup.id` is a formatted day key or host string — deliberately not the displayed `label`, which repeats across years/hosts and would collide as a `ForEach` id.

## Platform UI differences worth knowing before touching either

- **iOS** (`RootView`): one screen, a floating bottom `TabView` switches `mode` in place (plus a 4th "Affichage" tab that isn't a real destination — it just presents `SettingsSheet` and bounces the selection back). Swipe actions for delete/mark-read. Shake gesture (`ShakeGesture`, UIKit-only, iOS-only) cross-fades the whole UI to the next theme.
- **macOS** (`MacRootView`): a real `NavigationSplitView` sidebar (`MacSidebarView`) — "À lire" and "Lus" are plain rows, each shared source is its own row under a disclosed "Sources" group (not a shared expand-per-source screen the way iOS's Sources tab works), plus a "Classement" row (`MacSourceRankingView`) for the standing `SourceRank` tally. `MacFeedList` uses a context menu instead of swipe actions, toolbar buttons instead of iOS's floating circular ones, and wires "Marquer lu"/"Tout marquer comme lu" into the window's Edit > Annuler (`UndoManager` via `@Environment(\.undoManager)`) since macOS users expect that to work. Settings live in a real `Settings` scene (⌘,) — `MacSettingsView` — not a sheet.
- Both platforms' link row rendering goes through the one shared `LinkRowView` (rail/card/editorial layouts), with platform-specific tweaks passed in as parameters (e.g. `isSelected` for macOS's own selection-fill styling, `showHost` to suppress the redundant host line in a macOS single-source detail).

## Provisioning gotcha: don't re-diagnose SwiftData/SQLITE_AUTH failures from system logs alone

If a share extension fails to save with a `SwiftDataError`/`SQLITE_AUTH`-flavored error, the real cause is very likely a missing **App Groups** capability on that specific extension's provisioning profile (comparing `security cms -D -i .../embedded.provisionprofile` across targets — not just the compiled entitlements, which can look identical and correctly signed while the profile itself is missing the App Group key) — not a sandbox/TCC bug. Fix in Xcode's Signing & Capabilities for the affected target (toggle App Groups off/on with automatic signing to force a profile regen), and confirm the capability is enabled for that target's App ID on developer.apple.com too. This is a project-configuration issue, not something fixable in code.
